# 库存历史的存储开销

为 #48 选择新安装默认保留期时，使用真实 `Store::insert_history` 做一次离线写入测量。样本来自浏览器演示，不是实时 AutoDL 接口结果，不使用凭据。

```bash
cargo run --manifest-path src-tauri/Cargo.toml --example measure_history
```

示例在新的临时目录创建数据库，沿用当前表、索引和默认设置，按每区域每轮一个事务连续写入一天的样本，执行 WAL checkpoint 后比较主数据库大小，最后删除临时目录。不触碰真实应用数据库。

测量配置：默认 4 区（V100 专区、A800 专区、佛山区、北京 B 区）、60 秒一次、全天运行；[离线样本](history-profile.json) 每区分别有 2、2、4、6 个卡型，总共 14 个区域/卡型组合。

| 项目 | 结果 |
| --- | ---: |
| 每日查询轮数 | 1,440 |
| 每日库存行数 | 20,160 |
| 空库基线 | 45,056 bytes |
| 写入一天后（含索引） | 1,642,496 bytes |
| 每日增量 | 1,597,440 bytes，约 1.52 MiB |
| 30 天线性估算 | 约 45.7 MiB |
| 60 天线性估算 | 约 91.4 MiB |

因此新安装默认保留 **30 天**。已有设置不变，包括明确保存的 14 天和旧设置里尚无此字段的情况。用户可继续在设置中自行调整。

估算只针对历史表与索引。实际卡型越多、轮询越快、规则涉及的额外区域越多，占用越大；关机、睡眠和查询失败时没有写入。日志和其他应用数据会增加额外空间；SQLite 删除过期行后通常复用空页，不保证文件马上缩小。不同 SQLite/平台的页分配可能造成少量差异，线性估算不是上限。

热力图的“覆盖天数”按所选数据最早到最晚的本地日历日期计算，包含首尾日；“有采样天数”只计实际记录过数据的日期。两者分开显示，避免把关机期间的空白当成有效样本。实际采样不足 7 个日期时提示结论参考价值有限。浏览器加 `?demoHistoryDays=3` 可查看不足一周的状态。
